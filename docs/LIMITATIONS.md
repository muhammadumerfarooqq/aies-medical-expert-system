# Known limitations

Items are never deleted. When a limitation is fixed, its status changes to "SOLVED in <phase>".

| ID | Limitation | Why it exists | Viva defence | Planned fix | Status |
|---|---|---|---|---|---|
| L01 | Fever is a gate (required condition) for 5 of the 6 diseases, so afebrile cases such as pneumonia in older adults are missed. | The WHO/CDC descriptions we used define these diseases by fever; one uniform rule shape kept the knowledge base verifiable. | "We modelled the textbook presentation from WHO/CDC. The system tells the user when fever was missing (the hint), so it fails visibly, not silently." | Add afebrile rules for pneumonia after a review with a clinician. | OPEN |
| L02 | Dengue is capped at 0.63 with moderate fever (rule CF 0.90 x fever CF 0.70). | Rule CFs are multiplied by the weakest premise (MYCIN), and a moderate fever is 0.70. | "That is the MYCIN rule: a conclusion is never stronger than its weakest premise. The cap is why a lone symptom cannot give a confident diagnosis." | Review the intensity-to-CF table with a doctor. | OPEN |
| L03 | Certainty factors are expert-assigned from WHO/CDC descriptions, not clinically validated or learned from data. | The course asks for a knowledge-based system; no patient data was available. | "CFs encode how specific a symptom pattern is in the sources. They rank evidence; they are not probabilities. This is stated in the design document." | Calibrate with clinician feedback or a labelled data set. | OPEN |
| L04 | No knowledge-elicitation interview with a doctor. | Time and access. We used published fact sheets as the expert source. | "Fact sheets are what clinicians themselves cite; each rule carries its source." | Review the rules with a medical professional. | OPEN |
| L05 | "Confidence %" is a share among the matched diseases, not a probability: a single weak match shows 100%. | The teacher's format asks for a relative percentage among the shown diseases. | "We show the raw evidence strength (CF) next to it and explain the difference in a caption. Low evidence is visible even at 100%." | Show a warning when the best CF is low. | SOLVED in Phase 6B (evidence strength + caption in the chat UI and the CLI) |
| L06 | The engine ignores negative evidence: a symptom can never lower a disease's CF. | Only confirming evidence is modelled (design assumption 4). | "MYCIN-style CFs allow negative evidence, but we kept the model small and explainable. Absent symptoms simply do not add support." | Add disconfirming rules and the CF combination for mixed evidence. | OPEN |
| L07 | Only 6 diseases and 20 symptoms. | Scope of the course project. | "The engine is generic: a 7th disease needs only new JSON, with no code change (tested)." | Grow the knowledge base. | OPEN |
| L08 | CF combination assumes independent evidence. | The combination formula CF + c x (1 - CF) is only valid for independent rules (AIMA, overcounting). | "kb_verify enforces that rules concluding the same fact use disjoint root symptoms, so the assumption holds by construction." | None needed while the verifier stays. | OPEN |
| L09 | Severity is fixed per disease, not assessed per patient (design assumption 3). | Keeps the ranking explainable (safety-first). | "Severity ranks the disease type, not this patient; the red flags cover patient-specific emergencies." | Add patient factors such as age. | OPEN |
| L10 | Relative percentages assume the patient has one of the six diseases (design assumption 2). | Needed to compute a share. | "Stated on the result as a share among matched conditions." | None. | OPEN |
| L11 | Free-text input is synonym/keyword matching, not language understanding. | Standard library only, deterministic, explainable, offline. | "It is a dictionary built from the KB with word-boundary matching, so any behaviour can be traced and tested." | Add synonyms; optional spell-check list. | OPEN |
| L12 | Negation and duration handling is simple: a negation word applies to the whole clause, and "more than 3 days" is a single constant. | Keeps the parser small and testable. | "It handles the common patterns ('no fever', '5 days'); anything else falls back to asking via the picker." | Scope-aware negation; configurable duration threshold. | OPEN |
| L13 | English and Roman Urdu only. | The KB synonyms are in those two languages. | "Adding a language means adding synonyms to the KB; no code changes." | Urdu script synonyms. | OPEN |
| L14 | The Streamlit UI is single-user and local: no accounts, no saved history. | A course demo; a medical record store would need privacy design. | "Nothing is stored or sent anywhere; the app runs offline on localhost." | Optional export of a consultation. | OPEN |
| L15 | The CLI "Confidence %" column had no explanation. | Added later than the table. | "The same caption as the GUI is now printed under the table." | Done. | SOLVED in Phase 6B |
| L16 | Symptoms not in the knowledge base are reported and ignored (design assumption 6). | The engine can only reason with what the KB defines. | "They are shown to the user, never dropped silently." | Grow the KB. | OPEN |
| L17 | Afebrile presentations and one-symptom inputs return "not enough evidence" instead of a differential list. | A minimum amount of evidence is required for any diagnosis (display threshold 0.30). | "A refusal is safer than a guess; the hint names what is missing." | None. | OPEN |
| L18 | Severity defaults to Moderate when the user does not state it. | The severity step shows the default and lets the user change it, but a user who just presses Diagnose accepts it. | "The default is labelled 'default (not stated)' on screen, and the severity step is a mandatory stop before the diagnosis." | Ask about severity again when evidence is thin. | OPEN |
| L19 | Fuzzy typo matching is accepted automatically (similarity 0.75), so a misspelling can be read as a wrong symptom. | Typos are common when typing Roman Urdu. | "Every fuzzy reading is shown as 'Fever (read from bhukar)' on the severity step, so the user can see and remove it." | Ask for confirmation of low-similarity matches. | OPEN |
| L20 | Disease names typed instead of symptoms (for example "flu") are not understood. | The system works from symptoms by design: it must reach a disease by reasoning, not by being told one. | "A knowledge-based diagnosis starts from what you feel. Typing a disease name would skip the reasoning, so the app asks for symptoms." | None planned. | OPEN |
| L21 | The chain animation REPLAYS the engine's recorded trace so people can follow it. The engine itself finishes in milliseconds. | A full-speed run is unreadable. | "Say this up front: the animation is a replay of the trace the engine recorded, step by step. Nothing is computed during the animation." | None needed. | OPEN |
| L22 | Consultations are independent: a new sentence starts a new consultation. "Edit symptoms" and "Add more symptoms" are the ways to extend one. | Keeps each result tied to one clear set of inputs. | "Each result can be explained from exactly the symptoms shown on screen." | Optional merge of a follow-up sentence. | OPEN |
| L23 | Fever plus cough alone gives no result (the evidence stays below the 30% threshold). | Both symptoms are common and non-specific; the rules need more specific partners (for example body aches). | "A refusal is safer than a guess; the hint names what is missing." | Ask targeted follow-up questions when the evidence is thin. | OPEN |
| L24 | The text parser failed on sentences that mixed fillers, Roman Urdu and typos ("im having bhukar and flu"). | The first parser only tried the whole leftover phrase for a typo match. | "It now tries each word and each adjacent word pair, with the same similarity cutoff, and reports what it could not read." | Done. | SOLVED in Phase 6C |
| L25 | The first chat UI never asked how severe each symptom was, and the chain was a static list. | Earlier design assumed "moderate" for typed text. | "There is now a severity step before the diagnosis and the reasoning builds one step at a time." | Done. | SOLVED in Phase 6C |
| L26 | Typing is only available on step 1 (Symptoms). Later steps use buttons and selectors. | Keeps each result tied to the symptoms and severities shown on screen; "Edit symptoms" and "Add more symptoms" cover changes. | "A diagnosis should be explainable from the exact inputs on screen, so the wizard freezes them after step 1." | Optional free-text follow-up on step 2. | OPEN |
| L27 | The visual checks (layout, animation, Replay) were run in real Chrome with a throwaway Playwright setup that is not part of the project and is not in `requirements.txt`. The automated tests only check the HTML and state. | Keeping the project dependency-free; Playwright needs a browser. | "The repository has no extra dependencies. The browser checks were run once from a separate folder and are described in the report." | Add an optional browser test job. | OPEN |
| L28 | The earlier chat UI had text that was too small, panels that overlapped, a logo that could be invisible, and a Replay button that did not restart the animation. | Found by testing in Chrome; the first versions were only tested with a headless harness. | "The wizard was rebuilt and re-checked in Chrome at 1920x1080 and 1366x768: no page scroll, no overlap, text 15px or larger, and Replay remounts the panel." | Done. | SOLVED in Phase 6D |
| L29 | The layout is tuned for 1366x768 and larger screens. Below about 1280 px width the page may scroll, and phone width is not supported. | All sizes follow one scale variable that is tuned from 1366x768 upwards; the step layouts need that width side by side. | "It is a demo for a laptop or projector. The numbers were measured in Chrome at 1920x1080 and 1366x768." | A single-column layout for narrow screens. | OPEN |
| L30 | In the knowledge-base view at about 1366x768 the three example cards scroll inside their own area, and on step 3 the chain panels scroll inside themselves when a trace is long. | Large text plus the no-page-scroll rule leave too little height for every row at that size. | "Nothing is hidden: the content is there, inside a scroll area. At 1920x1080 it all fits." | Collapse rule lists on small screens. | OPEN |
| L31 | Crowded results (more than 3 conditions) use a compact layout with smaller text, stacked priority tiers and a scrolling card area. | Six cards at full size do not fit a window without page scrolling. | "The compact layout shows the same information (name, severity, confidence, evidence strength); only the size changes, and the banners and buttons stay visible." | A summary view plus drill-down. | OPEN |
| L32 | Severity cards for more than 9 symptoms are compact (name and selector on one row, one shared default note), and the side panel shows only a count for more than 6 symptoms. | 20 full-size cards do not fit on one screen. | "With many symptoms the typed sentence is not repeated; every symptom still has its own selector." | Group symptoms by body system. | OPEN |
